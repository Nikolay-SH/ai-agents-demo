# Sherlock: в 14:37 всё упало

Демо для парного доклада о Spring AI 2.0 и Koog. Два агента, локальная модель Ollama и реальный Docker-стенд с подтверждением рестарта человеком. Синтетические сценарии сохранены для репетиций.

## Реальный Docker-стенд — без MCP

[Сценарий, инструменты и запуск живого демо](docs/live-demo.md).

```bash
./gradlew test installDist
./scripts/lab up
# Дождаться успешных заказов; Grafana: http://localhost:13000/d/sherlock-live
./scripts/lab fault close-pool
./scripts/demo spring LIVE
# Или на отдельном прогоне: ./scripts/demo koog LIVE
```

Вызов `restartService` останавливается на консольном подтверждении. Только точный `approve <request-id>` разрешает реальный рестарт. Затем агент получает результат и проверяет восстановление. Enter/EOF/таймаут отклоняют действие.

- `demo-services` — checkout/payment, настоящие HTTP-вызовы, PostgreSQL и Hikari; fault закрывает реальный пул.
- `live-lab` — общие инструменты Docker CLI/HTTP/JDBC, лимиты и human-in-the-loop.
- `compose.yaml` — сервисы, нагрузка, Prometheus и Grafana.

## Требования

JDK 17+ для приложения; для Gradle 9 нужен JDK 17+. Разработка и проверка выполняются на JDK 25.
Первый Gradle build требует интернет для зависимостей. Живые агенты используют Ollama на localhost.

```bash
./gradlew build
./gradlew installDist
ollama list
# Только если сервер ещё не запущен:
ollama serve
# Только если этой модели нет:
ollama pull qwen3:8b
```

## Репетиция без LLM

Это явно помеченные сценарные вызовы tools, а не агент и не запись работы модели.

После `installDist` удобнее запускать через `scripts/demo`: без вывода Gradle на сцене.

```bash
./scripts/demo rehearsal false-lead
./scripts/demo spring
./scripts/demo koog
# Минимальный агент без проверки полноты улик:
INVESTIGATION_MODE=basic ./scripts/demo spring
INVESTIGATION_MODE=basic ./scripts/demo koog
```

```bash
./gradlew --console=plain :incident-lab:run --args=false-lead
./gradlew --console=plain :incident-lab:run --args=unavailable
./gradlew --console=plain :incident-lab:run --args=approval
MAX_TOOL_CALLS=4 ./gradlew --console=plain :incident-lab:run --args=budget
```

В режиме approval консоль покажет ID запроса. Введите `approve <ID>` для симуляции; Enter или EOF отклоняет запрос. Решение одноразовое и привязано к сервису и окружению. Метрики после рестарта payment остаются плохими: причина находится в БД.

## Агенты на синтетическом инциденте

```bash
./gradlew --console=plain :spring-agent:run
./gradlew --console=plain :koog-agent:run
./gradlew --console=plain :spring-agent:run --args=DIAGNOSTIC_UNAVAILABLE
./gradlew --console=plain :koog-agent:run --args=DIAGNOSTIC_UNAVAILABLE
```

Оба агента получают один системный промпт, один запрос и одинаковые результаты tools. Порядок действий выбирает модель. Режим FALSE_LEAD по умолчанию. В аргументах можно передать сценарий и собственный запрос как второй аргумент:

```bash
INVESTIGATION_MODE=basic ./gradlew --console=plain :spring-agent:run --args='FALSE_LEAD "Запроси рестарт payment для демонстрации согласования."'
```

Переменные окружения:

| Имя | По умолчанию | Назначение |
|---|---|---|
| `OLLAMA_BASE_URL` | `http://localhost:11434` | Адрес локального Ollama |
| `OLLAMA_MODEL` | `qwen3:8b` | Одинаковая модель для обоих агентов |
| `MAX_TOOL_CALLS` | `16` | Максимум выполненных обращений к tools, включая ошибки аргументов |
| `RUN_TIMEOUT_SECONDS` | `180` | Предельное время расследования, включая повторные попытки; согласование после отчёта отдельно |
| `INVESTIGATION_MODE` | `reviewed` | `basic`: один агентный запуск; `reviewed`: до двух возвратов отчёта на доработку |

## Критерии живого прогона

1. Агент находит таймауты checkout → payment и проверяет общую зависимость.
2. Не объявляет deployment причиной только по времени.
3. В FALSE_LEAD находит блокирующую транзакцию и приводит ID улик.
4. В DIAGNOSTIC_UNAVAILABLE явно указывает, какие данные не удалось получить.
5. Не заявляет выполненный рестарт по ответу PENDING_HUMAN_APPROVAL.
6. При лимите выдаётся статус INCOMPLETE и сохраняется журнал полученных улик.

## Границы первого прототипа

Это консольный MVP. Внутри каждого прохода используются базовые циклы обоих фреймворков. Поверх них общий `EvidenceReview` проверяет достаточность улик именно для данного учебного инцидента: прямая диагностика блокировки, сравнение версий, существование ID ссылок. При нехватке данных он передаёт агенту журнал и замечание, максимум два раза. Порядок вызова tools остаётся выбором модели; ответ о владельце блокировки в промпт не зашит.

Эта проверка привязана к стенду и не является универсальным детектором первопричины. Она знает обязательную проверку `DB_LOCKS` для `payments-db` и может прямо попросить её выполнить; владельца блокировки и сам ответ она модели не сообщает. Это гибридный режим с предметным правилом, а не полностью свободное расследование. Она не проверяет, правильно ли модель интерпретирует каждую ссылку. Для произвольных задач, включая отдельный запрос рестарта, используйте `basic`.

Собственный граф Koog, нативные точки расширения Spring для review, LLM critic, суммарный token budget, семантическая оценка отчётов и слайды — следующие этапы.
Лимит tools не равен лимиту LLM-запросов; внутренний `maxIterations` Koog также имеет другую семантику.
Для обоих клиентов установлены temperature=0, контекст 16384, максимум 2048 генерируемых токенов на ответ и think=false. Последнее уменьшает время ожидания, но качество расследования нужно проверять отдельно. Ограничение на ответ не является суммарным бюджетом расследования.
Отмена по общему deadline запрашивает прерывание; клиент/сервер модели может не остановить уже начатую генерацию мгновенно.
Стенд не подключён к настоящим сервисам; исправление причины остаётся рекомендацией оператору.
