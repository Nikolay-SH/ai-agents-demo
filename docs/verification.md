## Что показали эксперименты

Минимальные агенты действительно сами выбирают tools, но `qwen3:8b` иногда заканчивает на симптоме и рекомендует человеку доступную агенту проверку. Один усиленный промпт этого не устранил.

Поэтому сохранены два режима:

- `basic` — свободный минимальный агент. Может остановиться рано; полезен для первой сцены доклада.
- `reviewed` — общий контроль полноты улик для этого конкретного стенда. Он может прямо потребовать диагностику блокировок БД и возвращает неполный отчёт на доработку. Это осознанный переход к гибридной схеме.

Проверка принимает разные способы получить доказательство, что затронуты обе версии: сравнительные метрики, логи обеих версий или прямую диагностику, в которой перечислены блокируемые клиенты обеих версий. Она не требует единственного порядка вызовов.

## Ограничения, которые остаются

- Наличие достаточной трассы не означает правильность каждого предложения модели. В отчётах встречается раздел «проверенная альтернатива», который просто повторяет основную гипотезу.
- Финальный Koog-отчёт наряду с прекращением блокирующей транзакции предложил увеличение ресурсов БД. Это не следует из полученных улик и не устраняет показанную блокировку: следующий этап должен проверять смысл рекомендаций.
- В одном Koog-прогоне модель предложила перезапуск БД после обнаружения блокировки. Такое предложение требует проверки оператором; tool для рестарта БД запрещён политикой стенда. Автоматическая семантическая оценка рекомендаций ещё не сделана.
- Review сейчас общий для двух адаптеров. Явный граф Koog и реализация контроля через нативные точки расширения Spring — следующий этап, а не уже показанное преимущество одного стека.
- Лимит tools, ограничение генерации на ответ и wall-clock deadline работают на разных уровнях. Суммарный token budget ещё не реализован.
- Deadline запрещает дальнейшие tools и снимает ожидающие действия, но отмена уже начатой генерации зависит от клиента Ollama.
- Подтверждение оператора выполняется после отчёта в отдельном консольном шаге. Персистентного pause/resume агентной сессии пока нет.

## Ревью кода

Независимое чтение кода не выявило блокирующих проблем в рамках консольного MVP. Замечание по управлению ресурсами исправлено: Koog executor явно закрывает Ollama HTTP-клиент после каждой попытки, включая ошибку. После исправления сборка и создание дистрибутивов прошли повторно.

## Docker LIVE / human-in-the-loop (2026-09-10)

Добавлены реальные checkout/payment/PostgreSQL, нагрузка, Prometheus и Grafana. Сборка `./gradlew build` проходит; 28 тестов: 15 синтетического стенда, 2 HTTP/JDBC приложения, 11 бюджета и границы подтверждения.

`python3 scripts/check-live.py` успешно проверил HTTP 200 → закрытие настоящего Hikari → HTTP 503 → отказ без изменения bootId → подтверждение и новый bootId → HTTP 200. Решения в этой проверке вводил тестовый скрипт, не человек.

Prometheus сообщил `up` для checkout/payment, Grafana API вернул дашборд `sherlock-live` с четырьмя панелями. Проверен JDBC-инструмент к настоящему PostgreSQL. `scripts/lab up`, Docker Compose config и shell syntax проходят. При первой загрузке Docker Hub возвращал EOF; повторная загрузка образов завершилась успешно. Прямая команда docker build в scripts/lab обходит ошибку Compose Bake с не-ASCII путём проекта.

Независимое ревью обнаружило возможность запуска рестарта после активного deadline во время повторной Docker-проверки. Исправлено: проверки выполняются вне блокировки, финальный запуск процесса проходит через синхронизированный допуск с проверкой актуального бюджета. Регрессионный тест воспроизвёл проблему до исправления и проходит после; дополнительный тест проверяет последний допуск непосредственно перед запуском процесса.

LIVE не применяет фикстурный EvidenceReview и не гарантирует правильный вывод LLM. Ограничения времени/количества tools и допуск к рестарту обеспечивает обычный код.

При живом прогоне qwen3:8b однажды описала «запрос рестарта» только в тексте, не вызвав tool. Интеграционная проверка корректно упала, контейнер не изменился. Системный промпт уточнён, а итог теперь содержит фактический журнал из кода, независимо от утверждений модели. Это не гарантия исполнения намерений LLM: журнал показывает реальное действие или его отсутствие.

Другой прогон Spring AI/qwen3:8b действительно запросил рестарт checkout; тестовый ввод разрешил его. После рестарта агент заново вызвал status/metrics и увидел 9 запросов / 9 ошибок 503. Payment не перезапускался, интеграционная проверка восстановления упала. Это подтверждает работу HITL и одновременно показывает ошибочную гипотезу модели. Промпт уточнён: сначала исследовать upstream-зависимость; тестовый оператор теперь разрешает только payment, выбранный для данного fault-сценария. В обычном интерактивном режиме решение по checkout/payment принимает человек.

Финальный прогон Koog 1.2.0 + Ollama qwen3:8b с обновлённым общим промптом успешно завершил цикл: 10 native tool calls, запрос restartService(payment), тестовое подтверждение, реальный рестарт, getServiceInfo(payment) и getMetrics(payment) после рестарта. В последнем sample payment было 14 успешных запросов и новый bootId. Независимый harness проверил HTTP 200 у checkout и смену bootId payment. Трасса: captures/live-koog-approved.txt (локальная, ввод подтверждения автоматический). Стенд после проверки оставлен здоровым.

Итого: полная сборка и 28 тестов проходят; отказ и успешный рестарт общего механизма проверены на Docker; Spring native loop проверен на отказе и разрешённом, но неэффективном рестарте checkout; Koog native loop — на успешном восстановлении payment. Это демонстрационные прогоны, а не статистическая оценка качества фреймворков или модели.
