# Живой инцидент: Docker + human-in-the-loop

## Что происходит на самом деле

`checkout → payment → PostgreSQL`. Генератор нагрузки раз в секунду оформляет заказ. Сервисы реально вызывают HTTP и выполняют SQL; Prometheus собирает Micrometer, Grafana показывает запросы, ошибки и задержки.

Команда `fault close-pool` закрывает настоящий Hikari JDBC pool в payment. Процесс остаётся жив, но платежи и checkout отвечают 503. Это намеренное внедрение неисправности для воспроизводимого демо, а не имитация метрик. Перезапуск payment создаёт новый процесс и новый пул.

Spring AI и Koog используют нативные tool calls. MCP нет. Обе реализации вызывают общий Java-модуль `live-lab`:

| Tool | Реальный источник |
|---|---|
| `listServices()` | Docker Compose ps |
| `getServiceInfo(service)` | Docker inspect, HTTP /demo/status и Actuator health |
| `getMetrics(service)` | Actuator: HTTP-счётчики, JVM, uptime, Hikari |
| `getLogs(service, query)` | Docker logs, поиск в последних 120 строках за 5 минут, до 20 последних совпадений |
| `getDatabaseActivity()` | Фиксированный read-only запрос к pg_stat_activity |
| `restartService(service, reason)` | Консольное подтверждение, затем Docker restart по ID |

Агент не получает инструмент управления неисправностями и не знает причину из fixture. В LIVE не используется проверка EvidenceReview синтетического сценария.

## Запуск

Требуются Docker Compose, работающий Docker Engine, JDK 17+ и Ollama с `qwen3:8b`. Первоначальная сборка и загрузка образов требуют сети.

```bash
./gradlew test installDist
./scripts/lab up
./scripts/lab status
curl -X POST http://localhost:18081/checkout
# Открыть http://localhost:13000/d/sherlock-live
./scripts/lab fault close-pool
curl -X POST http://localhost:18081/checkout
./scripts/demo spring LIVE
# Для второго агента — повторно создать неисправность:
./scripts/lab fault close-pool
./scripts/demo koog LIVE
```

Запускайте агентов по очереди: у них один стенд. После `up` дождитесь ответа `/checkout` с HTTP 200. Prometheus нужны несколько scrape-интервалов, графику rate — до минуты.

## Решение человека

Когда агент вызовет `restartService`, консоль выведет проект, сервис, полный ID контейнера, причину и уникальную строку:

```text
approve <request-id>
```

Введите именно выведенную строку. Enter, любой другой ответ и EOF означают отказ. По умолчанию через 120 секунд ожидания запрос отклоняется. Отдельного approve-tool у модели нет. После отказа повторный запрос для этого сервиса в том же запуске запрещён.

Подтверждение связано с проектом `sherlock-live`, сервисом, ID контейнера и временем его запуска. Если контейнер успели заменить или перезапустить, подтверждение устаревает. Разрешены только checkout и payment. Модель не может передать произвольный shell или SQL.

Во время ожидания человек видит приглашение, а агент ждёт результат своего tool call. После разрешения tool выполняет рестарт, возвращает результат в тот же цикл; агент должен заново проверить сервис и HTTP-метрики. Под отчётом модели выводится фактический журнал действий из кода: он явно укажет, если restartService вообще не вызывался.

Успешный Docker restart и Actuator UP сами по себе ещё не подтверждают восстановление заказов.

Активное расследование ограничено 180 секундами и 24 вызовами tools. Время ответа человека не входит в эти 180 секунд; ожидание человека имеет отдельный лимит. Уже отправленную Docker-команду нельзя отозвать: при прерывании проверяйте фактическое состояние контейнера.

Настройки: `OLLAMA_MODEL`, `OLLAMA_BASE_URL`, `RUN_TIMEOUT_SECONDS`, `MAX_TOOL_CALLS`, `APPROVAL_TIMEOUT_SECONDS`. Скрипт сам устанавливает путь проекта.

## Проверка механики без модели

```bash
./scripts/demo live status
./scripts/demo live metrics payment
./scripts/demo live database
./scripts/demo live restart payment
```

Последняя команда — явно помеченный операторский harness. Он использует тот же реальный барьер подтверждения, но не является агентом. Полезен для проверки консоли перед выступлением.

`./scripts/lab reset` — ручной операторский рестарт двух приложений. `./scripts/lab down` останавливает стенд, сохраняя данные PostgreSQL.

## Сцена на двоих: 40 минут

| Время | Сцена |
|---|---|
| 0–4 | Здоровый checkout на графике. Второй спикер ломает пул. Зал выбирает первую диагностическую проверку. |
| 4–10 | Первый спикер показывает Spring AI: prompt, описания tools, реальный ход расследования. |
| 10–15 | Агент просит рестарт. Второй спикер нажимает Enter: ошибки остаются, действие не выполнено. Разбираете границу полномочий. |
| 15–22 | Koog на том же инциденте и tools: регистрация инструментов, цикл агента, отличие кода интеграции. |
| 22–28 | Подтверждение человеком, новый bootId, успешные checkout и восстановление графика. |
| 28–34 | Лимиты, устаревшее подтверждение, недостаточные улики. Что проверяет обычный код, что решает LLM. |
| 34–36 | Сравнение реализации и выводы из фактической трассы двух запусков. |
| 36–40 | Вопросы и резерв на задержки локальной модели. |

Не привязывайте реплики к точному порядку tools: его выбирает модель. Если она остановилась раньше или не запросила рестарт — это видимый результат прогона, а не повод выдавать операторский harness за работу агента. Для сцены подготовьте запись удачного настоящего запуска и подпишите её как запись.

## Автоматическая интеграционная проверка

```bash
python3 scripts/check-live.py          # операторский harness, без LLM
python3 scripts/check-live.py spring   # два настоящих запуска модели
python3 scripts/check-live.py koog
```

Проверка намеренно ломает локальный payment и автоматически вводит тестовые решения «отказать», затем «разрешить payment». Запрос на checkout тестовый оператор отклоняет: в этом сценарии причина находится в payment. Это проверка механики, а не запись решения живого человека. Скрипт сверяет HTTP 503/200 и bootId; трассы сохраняются в игнорируемом Git каталоге `captures/`. Запускайте на здоровом стенде и последовательно. Если модель не запросила рестарт, проверка падает и оставляет неисправность для исследования; восстановить можно ручной командой `scripts/lab reset`.
