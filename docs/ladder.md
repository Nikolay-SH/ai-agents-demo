# Лестница: от вызова LLM к агенту

Один живой инцидент и шесть шагов на двух фреймворках. Модель, системный промпт, вопрос, tools и правила проверки улик одинаковые
([Ladder.java](../live-lab/src/main/java/meetup/sherlock/live/Ladder.java)); меняется только код вокруг модели.

- Spring AI — [SpringLadder.java](../spring-agent/src/main/java/meetup/sherlock/spring/SpringLadder.java), по методу на шаг.
- Koog — [KoogLadder.kt](../koog-agent/src/main/kotlin/meetup/sherlock/koog/KoogLadder.kt), по функции на шаг.

## Инцидент: блокировка в БД

```bash
./scripts/lab up
./scripts/lab fault lock      # reporting-job: BEGIN; LOCK TABLE payments IN SHARE MODE; и висит idle in transaction
```

SHARE-блокировка пропускает SELECT, но блокирует INSERT. Платёж ждёт блокировку, через 2 с JDBC отменяет запрос, payment отвечает 503, checkout — 503.
Рестарт payment не помогает: процесс поднимается, health UP, заказы по-прежнему падают. Помогает завершение сессии reporting-job.
`./scripts/lab reset` снимает блокировку и перезапускает приложения; без него блокировка держится 15 минут.

## Шаги

```bash
./scripts/demo spring step0          # … step5; вторым аргументом можно передать свой вопрос
./scripts/demo koog step0            # то же на Koog
```

| Шаг | Что меняется в коде | Что показать |
|---|---|---|
| 0. Голый вызов | `model.call(prompt)` | Модель гадает и ссылается на улику `[E3]`, которой не существует |
| 1. Tools, цикл вручную | `ToolCallingManager` + цикл `for`, лимит 12 вызовов | Агент — это цикл; история — список сообщений: промпт растёт 471 → 4844 токенов. Модель останавливается на симптоме и советует человеку «проверить payment» |
| 2. История | `ChatClient` + `MessageChatMemoryAdvisor` внутри `ToolCallingAdvisor`, консоль оператора | Оператор отвечает — агент продолжает с уже собранными уликами. Под ответом видно, что в памяти: `{USER=2, ASSISTANT=11, TOOL=9}` |
| 3. Контекст | Тот же код, `LiveSession(compact=true)` | Логи: 120 строк → 2 строки с счётчиками. Метрики: окна 1m/20s из Prometheus вместо счётчиков с запуска. БД: кто кого блокирует. Модель всё равно делает по одному переходу на реплику — нужна стратегия |
| 4. Стратегия | Этапы задаёт код: симптомы → гипотезы → проверка каждой → отчёт | Код понижает CONFIRMED без реальной улики по сервису и идёт по зависимостям из живого `/demo/status`. Находит reporting-job без подсказки в промпте |
| 5. Критичные действия | `SpringActionTools`: `restartService`, `terminateSession`; даются модели только после подтверждённой причины | Консоль человека, отказ или подтверждение, затем код ждёт 20 с и запускает проверку восстановления |

Чтобы сравнить сырые и компактные ответы tools без LLM:

```bash
./scripts/demo live database
COMPACT=true ./scripts/demo live database
```

## Spring AI и Koog по шагам

| Шаг | Spring AI 2.0.1 | Koog 1.2.0 |
|---|---|---|
| 0 | `model.call(prompt)` | `executor.execute(prompt, model)` |
| 1 | Цикл `for` + `ToolCallingManager`, лимит — условие цикла | Цикл — граф из трёх узлов: `nodeLLMRequest` → `nodeExecuteTools` → `nodeLLMSendToolResults`, лимит — `maxAgentIterations` |
| 2–3 | `MessageChatMemoryAdvisor` внутри `ToolCallingAdvisor` | Фича `ChatMemory` + `agent.run(text, sessionId)` |
| 4–5 | Этапы — последовательные вызовы в Java-коде | Граф `triage → plan → verify ⇄ review → act → settle → recovery → report`: этапы — подграфы со своим набором tools, решения — узлы с обычным кодом, переходы — рёбра с условиями. Консоль показывает текущий узел |

Правила «CONFIRMED только с прямой уликой», «иди по зависимостям из `/demo/status`» и «действия только после подтверждённой причины» — общий код в `Ladder`, одинаковый для обоих.

## Граница полномочий (шаг 5)

- Модель только запрашивает действие. Решает человек строкой `approve <id>`; Enter, EOF, таймаут — отказ. Tool для подтверждения у модели нет.
- `terminateSession`: только сессия БД `sherlock`, которая сейчас блокирует другие (замер до 3 с). Подтверждение привязано к pid и времени старта сессии; если сессия сменилась или перестала блокировать — STALE.
- Одно решение на цель за запуск. Под отчётом — журнал действий из кода, а не пересказ модели.

## Что выяснилось на прогонах (qwen3:8b, 11.09.2026)

Записи — локальные `captures/ladder-step*.txt` (в git не попадают). Ввод подтверждений в шаге 5 делал тестовый скрипт, не человек.

- **Structured output блокирует tools.** С Ollama `.entity()` ограничивает формат ответа, и модель не может вызвать tool: первый прогон шага 4 не сделал ни одного вызова и выдумал улики `[3,4,5]`. Проверка кода понизила все вердикты до UNKNOWN. Решение — два вызова на этап: сначала tools и свободный текст, потом JSON без tools (`Conversation.result`).
- **Порядок advisors решает, что попадёт в память.** Память после `ToolCallingAdvisor` и отключённая внутренняя история — в памяти есть вызовы tools и их результаты. Иначе во второй реплике модель видит только собственный пересказ.
- **Снимок состояния может соврать.** Держатель блокировки «блокирует» только пока кто-то ждёт; payment ждёт 2 с из каждых ~3 с. Один снимок `pg_stat_activity` показал reporting-job без связи BLOCKS, и модель не подтвердила причину. Теперь сводка показывает удерживаемые блокировки и делает замеры до 3 с.
- **Ярлык модели ≠ её вывод.** В шаге 4 модель поставила payment CONFIRMED, а в объяснении написала, что зависимость в порядке. Правило «иди по зависимостям» в коде всё равно довело до payments-db.
- **Шаг 0 одинаков на обоих фреймворках.** Одна модель, temperature 0, один промпт — ответ слово в слово, включая выдуманную `[E3]`. Фреймворк начинает влиять только с шага 1.
- **Шаг 5 идёт разными путями.** В одном прогоне модель сразу запросила `terminateSession` → подтверждение → восстановление 0% 5xx. В другом — запросила рестарт payment, получила отказ, и итог честно сказал «восстановление не подтверждено». Оператор может продолжить разговор: «рестарт не дам, посмотри, кто держит блокировку».

### Koog 1.2.0

- **`think=false` теряется внутри подграфов.** Смена `toolChoice` пересоздаёт параметры через базовый `LLMParams.copy()`, и `OllamaParams.think` пропадает. qwen3 начинает «думать»: шаг 4 шёл 5 минут и упирался в лимит. Обёртка `NoThinkOllama` возвращает `think=false` в каждый запрос — после неё шаг 4 занимает ~2 минуты. Текстовый `/no_think` в промпте не помог.
- **`subgraphWithTask` падает на пустом ответе.** Этот подграф ждёт вызов finish-tool с типизированным результатом. qwen3:8b однажды вернула пустое сообщение — `IllegalStateException`, агент упал целиком. Этапы переписаны явными подграфами: цикл tools, затем запрос JSON; если JSON не разобран — видимое сообщение и безопасное значение по умолчанию.
- **Структурированный ответ требует объявить возможность модели.** Без `LLMCapability.Schema.JSON.Standard` в `LLModel` схема не уходит в Ollama, модель возвращает произвольный JSON — `MissingFieldException`.
- **Память хранит tools внутри сообщений.** Вызов tool — часть сообщения Assistant, результат — часть сообщения User; поэтому под ответом считаются части: `tool calls=8, tool results=8`.
- Прогон шага 5 на Koog: граф дошёл по зависимости до payments-db, `terminateSession` → подтверждение → 20 с → восстановление CONFIRMED.

Это отдельные наблюдения, не статистика. Модель выбирает порядок tools сама; для сцены держите запись удачного прогона, подписанную как запись.

## Время и лимиты

Шаг 0 — ~15 с, шаги 1–3 — 40–120 с на реплику (сырые ответы tools в шаге 2 заметно медленнее), шаги 4–5 — 1,5–3,5 мин. Активное время по умолчанию: шаг 1 — 180 с, шаги 2–5 — 300 с на весь диалог (`RUN_TIMEOUT_SECONDS` переопределяет). Ожидание человека и ввод реплик оператора в лимит не входят; 20 с ожидания перед проверкой восстановления входят.
